# Local Qwen ALARM replication

`cd_llm.experiments.alarm_claim_pools_local` runs a separate local Qwen3.5-9B replication of the frozen experiment in `results/20260920T150549Z/alarm_claim_pools/`. It imports observations, prompt templates, and the exact bytes of the 20 saved initial particle populations, but collects fresh answers. It never imports hosted answers or publishes paper changes.

The protocol uses all 37 ALARM variables, sample sizes 200 and 1000, observation seeds 1000–1009, and local, ancestry, and mixed claim pools. All three pools share the original inference seeds and 384-particle PC+GES initialization. Stated confidence is capped at 0.8 before both weighting and MH; raw confidence is retained. Acquisition uses working confidence 0.9. The engine bound remains 0.99 because that bound also applies to acquisition. Each of the 60 trajectories runs to 100 attempted queries; abstentions consume attempts and tokens without updating the posterior. Checkpoints at 10, 20, 50, and 100 are extracted without additional intermediate mutation.

Collection uses the pinned BF16 checkpoint and runtime recorded in the manifest, with temperature 0, seed 0, 256 output tokens, thinking disabled, and four concurrent requests. The request cache identity contains the complete messages, generation settings, model revision, and runtime fingerprint. The ephemeral loopback port is deliberately excluded so a continuation can reuse the cache. Six fixed pilot questions precede collection of all 3,330 outcomes. The shared parser permits one format repair; an invalid repaired answer stops collection, while an explicit abstention is complete.

The CLI stages are `submit`, `prepare`, `runtime-check`, `collect`, `audit`, `run-block`, `validate-pilot`, and `report`. Each accepts `--run-id`; inference blocks also accept `--block`. The automated chain checkpoints collection before its deadline, then audits every response through offline replay. Two inference pilot blocks and deterministic replay gate the remaining 18 blocks. Every evaluation and scoring stage uses the offline guard. Existing initializations are validated from their saved artifacts, independently of the jobs that produced them.

Outputs live in `results/<run-id>/alarm_claim_pools_local/`; command logs live in the corresponding timestamp under `out/`. `status.json` reports collection progress, throughput, ETA, and request accounting. The attempt ledger preserves requests with missing responses across restarts. Their unknown token usage is identified as unresolved rather than imputed. Returned usage includes repairs and abstentions. Actual API expenditure is zero; GPU allocation runtime is reported separately.

Completed outputs include per-run metrics, means and standard errors across ten seeds, claim diagnostics, response expenditure, paired ED contrasts with 10,000 bootstrap resamples, multiplicity-adjusted contrasts, audit records, and `alarm_claim_pool_efficiency_local.pdf`. The figure has separate query-cost and logarithmic token-cost columns with side legends. Uncertainty is conditional on this network and the shared expert collection. Local and hosted runs match the experimental protocol; their runtime implementations and generated answers need not be identical.

The recovery revision preserves the original run and forks its cache into a new timestamp. After the normal format-repair request, it accepts a flat answer/confidence/justification object missing only its final `}` if appending that delimiter produces valid JSON with unique keys and valid field values. Truncated generations and ambiguous content remain invalid. Raw response bytes and both requests' token costs are retained; recovered decisions carry an explicit audit tag. The recovery preparation replays all previously valid outcomes unchanged and records the parsing policy in the new manifest. Generation, confidence treatment, and inference are unchanged; this parsing extension is a recorded difference from the original hosted run.
